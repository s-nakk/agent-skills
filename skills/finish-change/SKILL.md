# 変更の仕上げ

目的は 2 つです。欠陥を人のレビューより前に見つけること。人の時間を、差分の通読ではなく、証拠の確認と判断が要る項目だけに使ってもらうこと。

人のレビューは数時間から数日かかる一番遅い確認です。ここで見つけられる欠陥をそこへ回すと、指摘、修正、再レビューの往復が人の時間を使います。

## 流れ

1. 検証する
2. 独立レビューにかける
3. 指摘を裏取りして仕分ける
4. 直して、確かめ直す
5. 記録を残す
6. 報告する

push、PR の作成、ready 化、人間のレビューへの返信の投稿、スレッドの resolve は、この手順に含みません。それぞれユーザーの指示で行います。draft PR ができた後の lens の実行は、この手順に含みます。

## 1. 検証する

- project に検証の skill があればそれを使います（どの project にどの skill を使うかは、規約の「プロジェクト固有」の節にあります）。無ければ `/verify`、それも無ければ project の lint・build・test を回し、振る舞いが変わる変更は実物を動かします
- 検証が通る前に 2 へ進みません。レビュアーの時間を、動かない変更に使わないためです

## 2. レビューにかける

どのレビューを、いつ、何回回すかは次のとおりです。ユーザーが skill 名を指定する必要はありません。指定があれば、その指定に従います。

| 段 | 見るもの | 使う skill | いつ | 回数 |
|---|---|---|---|---|
| A | 正しさ | `independent-final-review` | 検証が通った後、PR の前 | 初回は全体。以後は同じ reviewer に差分だけ。3 回まで |
| B | 構造と保守性 | `thermo-nuclear-code-quality-review` | 下の条件を満たす時だけ | 1 回 |
| C | チームの lens | project のレビュー lens（規約の「プロジェクト固有」の節にあるもの） | draft PR ができた時 | PR につき 1 回 |
| D | ユーザーが読む | `explained-diff-review` | 報告の時 | 1 回 |

**段 A の reviewer** は、新しいコンテキストで起動した Claude の subagent 1 本です。渡すのは対象範囲と手順、それに個人用のレビュー観点ファイル（`~/.claude/review/<リポジトリ名>/REVIEW.md`。ある project だけ）のパスだけです。リポジトリ名は、作業フォルダの名前ではなく `git remote get-url origin` の末尾から取ります（worktree のフォルダ名はブランチ名になっているため）。このファイルは、人のレビュアーが繰り返し指摘したことの一覧で、人より先に reviewer に拾わせるために渡します。実装の経緯や期待する結論は渡しません。レビューに効くのはモデルの違いではなく、書いた時の推論を見ていないことです。Codex を足すのは、ユーザーが指示した時と、危険度の高い変更（migration、認証・認可、外部システムとの契約、課金、CI や deploy の設定）の時だけです。

**段 B の条件**: 新しいクラス・層・抽象を足した。1 つのファイルやメソッドが大きく膨らんだ。条件分岐が増えた。変更が複数の層にまたがる。どれにも当たらない小さな修正では回しません。

**段 C** は、project にレビュー lens が決まっている時だけ回します。どの project で何を使うか、使わないかは、規約の「プロジェクト固有」の節にあります。そこに記載の無い project では、ユーザーが指示した時だけ回します。lens がある project では、ユーザーが PR の作成を指示して draft PR ができたら、続けて自動で回します。lens は PR へコメントを投稿します。修正の後に回し直すのは、**大きく直した時だけ**です（設計を変えた、複数のファイルに及んだ、新しい振る舞いを足した）。それ以外の修正は、段 A の reviewer に差分を見せます。

**レビュアーを足して重ねません。** 見落としがあった時は、同じ reviewer に前回の指摘と今回の差分を渡して続けさせます。別の reviewer を追加すると、同じ指摘の言い換えと古い欠陥の掘り起こしが増えます。同じ観点を複数の skill が見るので（正しさは段 A と lens の一部、構造は段 B と lens の一部）、3 の仕分けで重複をまとめます。

## 3. 指摘を裏取りして仕分ける

レビュアー、lens、Copilot の指摘は、そのまま信じず、そのまま直しません。1 件ずつ次を行います。

1. **裏を取る。** 指摘が挙げる `file:line` を開き、挙げられた条件で本当に起きるかを、コード、テスト、実行で確かめます。再現条件を書けない指摘は「未確認」として扱い、直しません
2. **重複をまとめる。** 同じ原因の指摘は 1 件にします。同じ種類の欠陥が他の場所にもあるなら、1 か所ではなく種類として扱います
3. **仕分ける。**

| 区分 | 条件 | すること |
|---|---|---|
| 直す | 裏が取れた。この変更が持ち込んだ。直し方に判断が要らない（受け入れ条件や規約から一意に決まる） | 直す |
| 判断が要る | 裏は取れたが、仕様・設計・範囲の選択が要る。または受け入れ条件や規約と衝突する | 直さず、選択肢と推薦を付けてユーザーへ |
| 対応しない | 裏が取れない、起こり得ない、影響が軽微、好みの問題、規約が逆を定めている | 理由を 1 文で残す |
| 既存 | 裏は取れたが、この変更が持ち込んだものではない | この変更では直さない。重大なら別の作業項目として提案する |

軽微な指摘（命名の好み、コメントの有無、整形）の扱い:

- 直すのは、この変更が触った行にあるものだけにします。触っていない行の指摘は「対応しない」か「既存」に入れます。人が読む差分を膨らませないためです
- 直す時は 1 つの commit にまとめます
- 軽微な修正だけの commit では再レビューを回しません。触った範囲の検証だけやり直します

## 4. 直して、確かめ直す

- 「直す」に入れたものを直し、触った範囲の検証（1）をやり直します
- 再レビューは、前回レビュー済みの位置からの差分だけを、段 A の同じ reviewer に見せます。全体を見直させません。すでに出た指摘を再び出させません。lens（段 C）を回し直すのは、大きく直した時だけです
- **再レビューが 3 回に達しても blocker が残る時は止めます。** 修正を重ねず、残った指摘と、収束しない原因の見立て（方針、設計、受け入れ条件のどれか）をユーザーへ渡します

## 5. 記録を残す

この段は、記録用の hook（`finish-gate.py`）を入れている端末だけで行います。入れていない端末では飛ばします。

検証と独立レビューが済み、修正を commit したら、その commit で次を実行します。

```bash
py ~/.claude/hooks/shared/finish-gate.py stamp --verified --reviewed
```

Windows では `py`、Mac では `python3` で起動します。

これは「この commit を検証し、レビューした」という印を、リポジトリとブランチごとのファイルに残します。PR を作る時と ready にする時に、hook が今の HEAD とこの印を比べ、合わない場合をログに残します（設定によっては止めます）。作業が複数のセッションにまたがっても、印は残ります。

- 実際に済んだ方だけを付けます。検証だけ済んだなら `--verified` だけ、後でレビューが済んだら同じ commit で `--reviewed` を足します。済んでいないものを付けません
- 未 commit の変更があると、記録は書けません。先に commit します
- 記録の後に commit を足したら、足した分の検証と再レビューを済ませてから、もう一度実行します
- 足した commit が軽微な修正だけ（3 の決まりで再レビューを回さないもの）なら、触った範囲の検証をやり直した上で、`--verified --reviewed` の両方を付けて構いません。レビュー済みの内容を変えていないためです
- 検証もレビューも要らない変更（文言だけ、docs だけ）は、理由を付けて記録します: `py ~/.claude/hooks/shared/finish-gate.py stamp --skip "docs だけの変更"`。記録が無い PR 作成は「飛ばした」と区別が付かないためです

## 6. 報告する

ユーザーが読むのはこの報告です。差分を読まずに判断できるように、次の順で書きます。

```markdown
## 判断が要る項目（N 件）
1. <何を決めるか>。選択肢 A（推薦）: …／B: …。根拠: `file:line`

## 検証の証拠
検証した commit: <sha>
<主張・確かめ方・結果の表、実行したコマンドと件数>

## レビューの結果
- reviewer: <判定>、<何回目>
- 指摘 N 件: 直した a、判断が要る b、対応しない c、既存 d
- 直したもの: <1 行ずつ>
- 対応しないもの: <理由を 1 行ずつ>

## 確かめていないこと
- <この手順が見ていない範囲。無ければ「なし」>
```

- 判断が要る項目を先頭に置きます。0 件なら「判断が要る項目はありません」と 1 行で書きます
- 「確かめていないこと」を必ず書きます。人が「どこを自分で見るべきか」を決める材料です
- 変更の危険度を 1 行で添えます。migration、認証・認可、外部システムとの契約、課金、CI や deploy の設定に触れた変更は、検証とレビューが通っていても、人が中身を見る対象として明記します
- ユーザーが差分を読む時は、上の報告を出した後に `explained-diff-review` の画面を作ります（段 D）。画面の形はその skill に従います
- PR に付いた指摘への返信と resolve は、`pr-review-response` skill があればその手順で行います。無ければ、返信の文面と resolve はユーザーの指示を待ちます

## 見落としを次に活かす

人のレビューで出た指摘は、個人用のレビュー観点ファイル（`~/.claude/review/<リポジトリ名>/REVIEW.md`）へ反映します（`pr-review-response` skill があれば、その §Approve の後 の手順）。2 件以上の PR で出た種類だけが観点になり、次からは段 A の reviewer が先に拾います。

本番や検証で、この手順が見逃した欠陥が見つかった時は、どの段が拾えたはずかを 1 行でユーザーへ伝えます。同じ種類が 2 回目なら、検証の skill、lint、hook のどこへ足すかを提案します。1 回だけの見逃しで規約を増やしません。
