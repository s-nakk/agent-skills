# テストケース網羅表

テストケースを、読み手が一目で判断できる表にする。判断したいことは 3 つある: 処理のどの分岐をどのケースが確かめるか、各ケースで何が返るか、ケースの無い分岐はどこか。

3 つ目を見せるために、横軸は**独立に変えられる因子と、その値**にする(§因子と値を決める)。横軸に「テスト 1 件の状況」を書くと、どの行も 1 列にだけ印を付け、表が対角線になる。それでは、試していない値や組み合わせが見えない。

使う場面は 2 つあり、表の形は同じ:

| モード | いつ | 入力 | 表の行 |
|---|---|---|---|
| 計画(`mode: "plan"`) | 設計・仕様が固まった後、実装の前 | 仕様、受け入れ条件、設計、触る予定のコード | 予定のテストケース。合意 → Red → Green の状態を持つ |
| 確認(`mode: "review"`、既定) | PR を出す前後 | PR の差分とテスト | 実際に足した・変えたテスト |

計画モードの手順は §計画モード、TDD での使い方は §TDD で進める、確認モードは §確認モードの手順 を読む。書き方の決まり(§書き方の決まり)と組み立て方(§組み立てて確かめる)は両方に共通。

ページは固定のテンプレート(`assets/matrix-template.html`)で作る。Claude が書くのは表の中身のデータ(`matrix.json`)だけで、色分け・件数の集計・組み合わせ表・ケースの無い値とマスの赤表示はテンプレートとスクリプトが行う。データの形は [references/data-format.md](references/data-format.md) を読む。

## 計画モード

実装の前に、仕様からテストケースを作り、ユーザーと合意する。合意したケースが、TDD で最初に書く失敗するテストの一覧になる。表があると、読み手は「この分岐にケースがあるか」「期待値はこれでよいか」を条文を読み比べずに判断できる。

### 1. 入力を集める

- 仕様(SDD、spec、作業項目の受け入れ条件)、設計(ADR、設計メモ)、触る予定の既存コード、外部システムの契約。
- プロジェクトのテストの規約。どのテストレベル(単体、結合、E2E)で何を確かめるか、テストファイルの置き場所と命名、テストデータの作り方。プロジェクトがテストケース合意の形(必要な項目)を定めていれば、それに合わせる。
- 仕様にまだ書かれていない分岐に気づいたら、ケースを作る前にユーザーに聞く。テストケースで仕様を勝手に決めない。

### 2. 因子・値とケースを作る

- 横軸の因子と値は、仕様の分岐、受け入れ条件の Given、境界(ちょうど・1 つ外)、失敗の経路(入力の誤り、対象が無い、外部システムの 4xx・5xx・タイムアウト・形の誤り、同時実行)から作る。作り方は §因子と値を決める。
- 結果が 2 因子の組み合わせで決まるところには組み合わせ表を付け、空いたマスにケースを足すか、理由を付けて対象外にする。
- 1 行 = 1 ケース。`action` に前提と操作、`result` と `detail` に期待する結果を、仕様の値で具体的に書く(§書き方の決まり)。`covers` に、そのケースが固定する因子の値を書く。`guard` に、そのケースで確かめる観点を「〜こと」の形で書く(ページでは「観点:」の後に出る)。起きてほしくない事故の形(「締めた月の請求書を書き換える」)で書かない。否定の事故の文は期待する結果と取り違えやすく、否定が重なると読めない。○「締めた月の請求書を書き換えないこと」「注文の無い顧客にも請求書を作ること」`status` は `planned`。
- `kind` は、プロジェクトの規約で決まるテストレベル。表ごとに `placement` へ配置先のテストファイルを書く。
- 重複を作らない。同じ値の組み合わせを同じ層で確かめるケースは 1 つにする。下の部品で確かめれば足りる値を、上の層でも確かめる場合は、上の層で確かめる観点を `guard` に書く(例:「DB の前月の請求書を読んで、繰越額を求めること」)。
- ケースの無い値と組み合わせは 0 にする。テストしない値を残すなら、理由を表の `note` に書き、報告で挙げる。テストしない組み合わせは `excluded` に理由を書く。

### 3. 独立レビューにかける

ユーザーに見せる前に、表を作った経緯を知らない reviewer(新しいコンテキストの subagent 1 本)に、過不足を確かめさせる。表を作った本人は、自分が思いついた分岐しか表にできず、同じ思い違いのまま「網羅した」と判断するため。

渡すもの: `matrix.json` のパス、受け入れ条件と仕様の場所(作業項目、spec、設計メモ)、触る予定のコードの場所、プロジェクトのテストの規約と、あれば既存テストの一覧や受け入れ条件の一覧、個人用のレビュー観点ファイルがあればそのパス(`~/.claude/review/<リポジトリ名>/REVIEW.md`。リポジトリ名は `git remote get-url origin` の末尾から取る)。会話の経緯、表を作った時の判断、期待する結論は渡さない。reviewer はファイルを編集しない。

確かめさせること:

| 観点 | 見るもの |
|---|---|
| 不足 | 受け入れ条件の 1 項目ずつに、それを確かめるケースがあるか。仕様と設計にある分岐、失敗の経路、境界、逆のケース(正常を確かめたら異常)にケースがあるか。その条件を実装から消しても落ちるケースが無い分岐はないか |
| 冗長 | 同じ因子の値の組み合わせを、同じ層で確かめるケースが複数ないか。下の層で確かめた値を、上の層で観点なしに繰り返していないか。既存のテストがすでに確かめていることを、もう一度足していないか |
| 価値 | 定数、設定、定義の中身を書き写して確かめるだけのケースはないか。受け入れ条件にも仕様にも無い、起こり得ない状態のためのケースはないか |
| 層と配置 | 各ケースのテストレベルと配置先が、プロジェクトの規約に合うか。結合で確かめるべきことを単体に、単体で足りることを結合に置いていないか |
| 期待値 | 期待する結果が、受け入れ条件と仕様の値と一致するか。仕様に無い値をケースが勝手に決めていないか |

reviewer は、指摘ごとに、表の通し番号(足す場合は入れる表と因子の値)、根拠(受け入れ条件の番号、仕様の箇所、既存テストの名前)、提案(足す・消す・まとめる・層を変える・期待値を直す)を返す。

指摘は、根拠を開いて裏を取ってから表へ反映する。裏が取れない指摘、受け入れ条件や仕様が決めていないことを決めようとする指摘は反映せず、ユーザーへの質問にする。反映したら、変えた行だけを同じ reviewer に見せて確かめる。やり取りは 2 回までとし、それでも食い違う点はユーザーへ持っていく。

### 4. 合意する

1. 組み立てて公開する(§組み立てて確かめる)。データは、セッションをまたいで使えるように `~/.claude/test-case-plans/<リポジトリ名>/<ブランチ名か作業項目>/matrix.json` に保存する。リポジトリの中には置かない。
2. ページの URL と、ケース数、ケースの無い値と組み合わせ、対象外にした組み合わせとその理由、判断に迷った期待値を報告する。ケースはページの通し番号(#1 から。テンプレートが全行に付ける)で示す。独立レビューの結果も添える: reviewer の指摘で足したケース、消した・まとめたケース、反映しなかった指摘とその理由、ユーザーに決めてほしい点。
3. AskUserQuestion で合意を取る。選択肢は「この計画で進める」「直してほしい」。**合意の前にテストコードを書かない。**
4. 直すときは、変えた行を示して再び合意を取る。

## TDD で進める

合意した計画を、上から 1 行ずつ(大きければ表ごとに)次の順に進める。

1. **Red:** そのケースのテストを書いて実行し、期待どおりの理由で失敗することを確かめる。コンパイルエラーや別の理由の失敗は Red に数えない。`status` を `red` にする。
2. **Green:** テストが通る最小の実装をする。`status` を `green` にする。
3. **Refactor:** Green を保ったまま整理する。

表ごとに区切りがついたら組み立て直して同じファイルパスで再公開し、計画・Red・Green の件数で進み具合を見せる。実装の途中でケースを足す・変える・消す必要が出たら、変える行を示して再び合意を取ってから書く。

PR を出す前に、確認モードで実際のテストを集め、計画と突き合わせる。計画にあってテストが無い行、計画に無いテストを報告する。

## 確認モードの手順

### 1. 範囲を決める

- PR の base、head、変更されたファイルを取る: `gh pr view <番号> --json baseRefName,headRefOid,files`。差分は `git diff <merge-base>...<head>` で読む。スタックした PR では base が main とは限らないので、PR の base ブランチとの merge-base を使う。
- 対象のテストは、PR で足したテストと、PR で中身を変えたテスト。変更したファイルの中でも、diff が触れていない既存のテストは対象にしない(ただし下の「この変更の外のテスト」は別)。
- テストが確かめている本番コードのファイルを特定する。テストの Arrange と Act から、呼んでいるクラスとメソッドをたどる。

### 2. 処理が分かれる因子と値を洗い出す

本番コードを読み、結果が変わる分岐をすべて挙げる。if、switch、catch、早期 return、入力の検査の失敗、外部システムの応答の種類(成功、4xx、5xx、タイムアウト、形の誤り)、保存の分岐(追加、上書き、何もしない)、定期ジョブの境界。受け入れ条件(`[AcceptanceCriteria]` 属性や作業項目の受け入れ条件)の Given も候補にする。挙げた分岐を、§因子と値を決める に従って因子と値にまとめる。

因子と値は、テストが用意する入力や状態で書く。「関数が HTTP 400 を返す」のような結果は因子にしない。結果は行の `result` と `detail` に書くもので、因子に入れると、その結果を確かめるテストが無いことが「テストの無い値」として正しく見えなくなる。ある層の分岐を下の部品のテストだけが確かめているとき(部品はエラーを返すが、それを受け取った関数が 400 にすることは誰も確かめていない、など)は、上の層の因子を「関数が受け取る本文」のように入力で立て、値「コマンドを作れない」に行が無ければ空いたままにする。

因子は処理の段階ごとの表(section)に分ける。段階は処理の順に並べる。例: 要求の受け付け(HTTP 関数)→ 処理の前の検査 → 外部システムの呼び出しと失敗 → 応答の読み取り → 保存 → 定期ジョブ → 共通の仕組み。1 つの表の値の列は多くても 12 前後にする。多いときは段階を分ける。

### 因子と値を決める

計画モードでも確認モードでも同じ手順で決める。データの書き方は [references/data-format.md](references/data-format.md) §因子と値・§組み合わせ表。

1. **因子は、結果を変える入力や状態を 1 つずつ取り出す。** 「注文の状態」「在庫引当の状態」「実行の時刻」「倉庫の数」など。1 つの因子に 2 つのことを混ぜない。×「片方の入力が失敗し、もう片方が未確定」(2 因子の組み合わせ)、×「決済照会エラーの注文を手動で照会し、また失敗する」(テスト 1 件の状況)。
2. **値は、同じ振る舞いになるまとまり(同値クラス)と、その境目にする。** 状態の一覧をそのまま値にせず、結果が同じになるものはまとめる(決済済・注文なし・取消済 → 「確定」)。境目は値として立てる(「終わる 1 秒前」「終わりちょうど」)。まとめた中身は `terms` か `note` に書く。
3. **各行は、自分が固定した値にだけ印を付ける。** そのテストで意味を持たない因子は書かない。
4. **結果が 2 因子の組み合わせで決まるところには、組み合わせ表を付ける。** 例: 2 つの入力の状態(どちらが失敗でも失敗、片方でも未確定なら待つ)、実行の時刻 × 前日の状態。3 因子以上は 2 因子ずつに分ける。起こり得ない、または別の表で確かめる組み合わせは、`excluded` に理由を書く。
5. **組み立てたら、対角線になっていないかを見る。** 因子が 2 つ以上あるのに、どの行も 1 列にしか印が無く、どの列も 1 行にしか印が無いなら、列が「テスト 1 件の状況」になっている。`build_matrix.py` はこの形を警告する。因子と値に分け直す。因子が 1 つの表(呼ぶ人の役割ごとに 1 件、など)は、1 行 1 列で正しい。ただし、その 1 つの因子の値が状況の寄せ集めになっていないか(値どうしが同じ軸の上にあるか)は見る。

### 3. テストを行にする

各テストの Arrange、Act、Assert を読み、そのテストが固定する因子の値(`covers`)と、確かめている結果(`result`、`detail`)を書く。

- **`detail` には、そのテストの assertion が確かめていることだけを書く。** 本番コードを読めば分かる結果でも、テストが確かめていなければ書かない。たとえば部品の単体テストの行に「関数は HTTP 400」と書くと、関数のテストが無いことを表が隠してしまう。
- **メッセージの文面は本番コードの文字列から写す。** テストが部分一致(`ShouldContain`)で確かめていても、本番コードの組み立てを読んで全文を書く。毎回変わる部分(ID、時刻)は `{ID}` や `…` にする。
- **日時と数はテストの定数から取る。** テストクラスごとに固定した現在時刻が違うことがある。推測で書かない。
- **Theory は 1 行にまとめ、件数を「(3 件)」で添える。** 行ごとに結果が違うなら、`detail` に並べるか、行を分ける。
- **同じテストを複数の表に載せるとき、2 回目以降は `cases: 0` にする。** 合計が二重にならない。
- **この変更の外のテストがその値を確かめているとき(共通の部品を使う場合)は、`kind: "s"`、`cases: 0` の行を足し、`action` にどの機能のテストかを書く(例:「注文一覧の読み取りのテスト」)。** そのテストが実在し、その値を本当に確かめていることを読んで確かめる。
- **テストのクラス名やメソッド名はページに載せない。** 読み手は「何をして、何が返るか」で判断する。名前は表を作る途中の照合にだけ使う。
- **この作業で足したテストは `added: true`、中身を変えた既存のテストは `changed: true` にする。** 「以前は〜だった」のような経緯は `detail` に書かない。表は今のテストが何を確かめているかを示すもので、変えたことは印で分かる。
- テストの種類(`kind`)は、`u` 単体(ホストも DB も使わない)、`i` 結合で外部システムの応答をテストで用意する、`k` 結合でモックや実物の外部システムを実際に呼ぶ、`s` この変更の外のテスト。

### 4. 報告する

- ページの URL と、合計のケース数、テストの種類ごとの件数。
- `uncovered_values`(テストの無い値)と `uncovered_combinations`(テストの無い組み合わせ)。あれば、テストを足すか、理由を付けて対象外にするかを AskUserQuestion で聞く。黙って足さない。
- 表を作る途中で、同じ値の組み合わせを同じ層で二重に確かめているテストに気づいたら、消してよいかを提案する。黙って消さない。
- 計画モードで合意した計画があれば、計画の行と実際のテストを突き合わせた結果。計画にあってテストが無い行、計画に無いテスト、期待値が計画と違うテスト。
- 確かめられなかったこと(読めなかったテスト、照合できなかった値)。

## 書き方の決まり

読み手はコードを読まずに表だけで判断する。そのために次を守る。

- **日本語で書く。** クラス名、メソッド名、エラーの code、メッセージの文面は原文のまま。
- **造語や略語を作らない。** 「差し替え」「境界」「1 秒前」のような、文脈が無いと意味が取れない言い方を見出しや行に使わない。英語の名前を訳して新しい言葉を作らない(envelope を「封筒」とするなど)。訳すと、読み手はコードにもドキュメントにも無い言葉を覚えることになる。ドメインやコードの言葉(「締め日」「繰越」など)を使うときは、`terms` で定義する。`terms` は「日本語(識別子)」の順で書く。
- **定着した用語は訳さない。主語の無い名詞句を作らない。** ステータス、ジョブ、キュー、メッセージ、outbox のような開発で定着した言葉は、そのまま使う(×「状態」「依頼を積む」)。処理は「何の処理か」が分かる名前で呼び、名前を初めて出すところで識別子を添える(○「請求書生成ジョブ(`GenerateMonthlyInvoices`)」、2 回目から「生成ジョブ」 ×「作成の実行」)。動詞も普通の言い方にする(○「生成ジョブを実行する」「メッセージを outbox に登録する」 ×「作成の実行を動かす」)。
- **内部の型、メソッド、設定の名前を因子・値や行に書かない。** `ISender`、`TryLockAsync`、`RetryPolicy` のような名前は、コードを読まない人には意味が取れない。外から見える振る舞い(「請求書の作成を実行しない」「ロックを 4 秒だけ待つ」)で書く。原文のまま書くのは、要求や応答の項目名(`customerId`)、エラーの code、メッセージ、結果の種類(`Invalid` など)、DB を更新するケースのテーブル名と列名だけ。どうしても識別子が要るなら `note` か `terms` に置く。
- **主語と条件を省かない。**
  - 因子は主語の入った名詞句、値はその因子の中で意味が通る言葉で書く。○ 因子「注文の日時」、値「締め日より 1 秒遅い」 ×「締めの 1 秒後」
  - 行は「どんな状態で、何をするか」で書く。○「注文の日時を締め日より 1 秒遅くする」 ×「1 秒後は OutsidePeriod」
  - 表の見出しは、その段階で何をしているかの文で書く。○「取り込みの前に、指定された期間を確かめる」 ×「期間」
- **量には向きを書き、結果の数は計算の筋道を添える。** 「数量 30」だけでは入庫か出庫か読めない。○「出庫 30 個の注文」「入庫 300 個の発注」。上限や残りの数が結果になる行は、どこから出た数かを 1 文で書く(○「在庫 100 個では注文 300 個のうち 100 個しか引き当てられず、残りの 200 個を在庫不足にする」)。
- **期待値を抽象化しない。** `result` に結果の種類(`Ok`、`Invalid`、`HTTP 400`、`契約違反` など)、`detail` に code、メッセージの文面、呼び出しの回数、行数、保存した値を書く。×「エラーを返す」「正しく保存される」
- **期待値は簡潔に。** 1 行に入る長さを目安にし、前置きや言い換えを足さない。
- **状態が変わるケースは、前の状態と新しい状態を両方書く。** 「状態が変わると」「確定になると」だけでは、どこから変わったのかが読めない。因子にも「前の状態」を立てる。○「決済待ち → 決済済」「決済照会エラー → 決済照会エラー(変わらない)」
- **DB を更新するケースは、何が変わるかを抽象化せず、テーブル・列・値で書く。** 列の更新は「テーブル.列: 前 → 後」、行の追加と削除は「テーブル に N 行追加(列 = 値)」「テーブル の N 行を削除」と書く。変えないことを確かめるなら「テーブル.列 は 前 のまま」「テーブル の行数は N のまま」と書く。この場合に限り、テーブル名と列名は原文のまま書いてよい。○「`Order.Status`: WaitingForPayment → Paid、`OutboxMessage` に 1 行追加(`TargetQueueName` = generate-monthly-invoices-queue)」 ×「注文は決済済になる。作成の実行の依頼を 1 件積む」
- **前提は `note` に具体的な値で書く。** テストで固定した時刻、上限の値、境界の計算(例:「現在 2026-11-04 05:00:00、90 日前は 2026-08-06 05:00:00」)。

## 組み立てて確かめる

1. `matrix.json` を書く。リポジトリの中には置かない。確認モードはセッションの scratchpad、計画モードは `~/.claude/test-case-plans/<リポジトリ名>/<ブランチ名か作業項目>/`(TDD の間、セッションをまたいで更新するため)。
2. 組み立てる: `python <skill>/scripts/build_matrix.py <dir>/matrix.json <dir>/test-matrix-<PR番号か作業項目>.html`。エラーが出たら直し、警告(計画で `guard`・`status`・`placement` が無いなど)を読む。件数、テストの無い値と組み合わせの報告は、HTML の隣の `<HTML のファイル名>.report.json`(UTF-8)を Read で読む。標準出力にも同じものが出るが、シェルによっては日本語が化ける。
3. 確認モードでは、報告の `cases` の合計を、変更に含まれるテストの実際の件数と突き合わせる(テスト結果のファイル、テスト一覧の生成物など)。合わなければ、数え漏れか二重計上を直す。
4. 確認モードでは `detail` の値をテストの assertion と本番コードの文字列で、計画モードでは仕様の値で、1 件ずつ照合する。特に日時、件数、メッセージの文面。
5. Artifact ツールで公開する。初回は `icon: "table"` と 1 文の `description` を付ける。更新は同じファイルパスで再公開して、同じ URL を保つ。Artifact ツールが無い環境(Codex など)では、HTML ファイルの絶対パスを渡す。

## 出力の言語

ページも報告も日本語。英語の文面(メッセージ、識別子)は原文のまま載せる。
