# データの形(matrix.json)

`scripts/build_matrix.py` が読むファイル。キーは英語、値は日本語で書く。

```json
{
  "title": "月次請求書作成テスト網羅表",
  "scope": "PR #12(作業項目 345)の head 1a2b3c4d5 時点のテストです。",
  "kind_labels": {
    "i": "結合テスト(外部の応答はテストで用意した値)"
  },
  "terms": [
    { "term": "確定・失敗・未確定", "definition": "入力の状態の 3 つの分け方。…" }
  ],
  "sections": [
    {
      "title": "4. 作成の実行: 2 つの入力の状態で、何をするかを決める",
      "placement": "GenerateMonthlyInvoicesHandlerTests.cs",
      "note": "倉庫 2 件の顧客。実行は締め日の前(前日 22:00 JST)。",
      "factors": [
        { "name": "注文の状態", "values": ["確定", "失敗", "未確定"] },
        { "name": "在庫引当の状態", "values": ["確定", "失敗", "未確定"] }
      ],
      "combinations": [
        {
          "factors": ["注文の状態", "在庫引当の状態"],
          "excluded": [
            { "values": ["確定", "確定"], "reason": "両方が確定した場合は、表 7 で区間の中身まで確かめる" }
          ]
        }
      ],
      "rows": [
        {
          "action": "注文を決済照会エラー、在庫引当を引当済にして、請求書生成ジョブを実行する",
          "outcome": "error",
          "result": "Error",
          "detail": "請求書は 2 件とも作成エラー(inputFailed、input=order、status=PaymentInquiryError)",
          "kind": "i",
          "covers": { "注文の状態": "失敗", "在庫引当の状態": "確定" },
          "cases": 1,
          "added": true
        }
      ]
    }
  ]
}
```

## 各キー

| キー | 内容 |
|---|---|
| `mode` | 任意。`plan`(実装前の計画)か `review`(PR のテストの確認、既定)。`plan` では見出しや集計の文言が「予定のケース」に変わる |
| `title` | ページの名前。2〜4 語の名詞句(例: 「月次請求書作成テスト網羅表」)。説明は付けない |
| `scope` | 何時点のどのテストかを 1 文で。PR 番号、作業項目、head の短い SHA を入れる |
| `kind_labels` | 任意。凡例の文言を、対象に合わせて上書きする(外部システムの名前を入れるなど)。キーは `u` `i` `k` `s` |
| `terms` | この表で使う言葉と、その定義。1 つ以上を推奨 |
| `acceptance_criteria` | 任意。受け入れ条件のうち、テストが確かめている件数と総数 |
| `sections[].title` | 処理の段階を、何をしているかの文で書く。番号は処理の順番を表すときだけ付ける |
| `sections[].factors` | 横軸。結果を変える独立した因子と、その値。§因子と値 |
| `sections[].factors[].name` | 因子の名前。主語の入った名詞句(「注文の状態」「実行の時刻」)。表の中で一意 |
| `sections[].factors[].values` | 因子の値。同じ振る舞いになるまとまり(同値クラス)と、その境目。因子の中で一意 |
| `sections[].combinations` | 任意。結果が 2 つの因子の組み合わせで決まるとき、その 2 因子の組み合わせ表。§組み合わせ表 |
| `sections[].combinations[].factors` | 組み合わせる 2 つの因子の名前。1 つ目が表の縦、2 つ目が横 |
| `sections[].combinations[].excluded` | 任意。テストしなくてよい組み合わせ。`values`(2 つの値)と `reason`(理由)を必ず書く |
| `sections[].note` | 任意。表を読むのに要る前提(テストで固定した時刻、上限の値など)。具体的な値で書く |
| `sections[].placement` | 計画で推奨。この表のテストを置くテストファイル。テストレベルが分かれるなら「単体: … / 結合: …」と書く |
| `rows[].action` | テストでしていること。「どんな状態で、何をするか」を書く。Theory の行をまとめるときは件数を「(3 件)」で添える |
| `rows[].outcome` | `ok`(正常に終わる)か `error`(エラーで終わる)。ページでは緑と赤の札になる |
| `rows[].result` | 結果の種類を短く。`Ok`、`Invalid`、`HTTP 400`、`契約違反`、`Conflict` など。札の中に入る |
| `rows[].detail` | 具体的な値。エラーの code、メッセージの文面(「」で囲む)、呼び出しの回数。DB を更新するケースは「テーブル.列: 前 → 後」「テーブル に N 行追加(列 = 値)」の形で、テーブルと列を名指しする |
| `rows[].kind` | `u` 単体、`i` 結合(外部の応答をテストで用意)、`k` 結合(モックや実物を実際に呼ぶ)、`s` この変更の外のテストが確かめる |
| `rows[].covers` | この行が固定している因子の値。`{ "因子の名前": "値" }`。Theory で 1 つの因子に複数の値を当てるときは配列(`["失敗", "未確定"]`)。行が固定しない因子は書かない |
| `rows[].cases` | この行のテストの件数(Theory は行の数)。同じテストを別の表にも載せるときは、2 回目以降を 0 にする。`s` は 0 |
| `rows[].added` | 任意。この作業で足したテストなら `true`。「追加」の印が付く |
| `rows[].changed` | 任意。この作業で中身を変えた既存のテストなら `true`。「変更」の印が付く。`added` と同時には付けない |
| `rows[].guard` | 計画で推奨。このケースで確かめる観点を「〜こと」の形で書く(例:「確定前に請求書を消さないこと」「締め日ちょうどの注文を受け付けること」)。事故の形で書かない。行の下に「観点:」の札で小さく出る |
| `rows[].status` | 計画で推奨。`planned`(合意済み、テスト未作成)、`red`(テストを書き、期待どおりの理由で失敗を確認)、`green`(実装して通った)。札で出て、上に件数が出る |

## 因子と値

横軸は「このテストだけの状況」ではなく、**独立に変えられる因子と、その値**にする。各行は、そのテストが固定している値に印を付ける。こうすると、1 つの行が複数の列に印を付け、1 つの列に複数の行が印を付ける。どの値にテストがあり、どの値に無いかが列で見える。

- **因子は、結果を変える入力や状態を 1 つずつ取り出したもの。** 「注文の状態」「在庫引当の状態」「実行の時刻」「倉庫の数」など。1 つの因子に 2 つのことを混ぜない(×「片方の入力が失敗し、もう片方が未確定」は 2 因子)。
- **値は、同じ振る舞いになるまとまりと、その境目。** 状態の一覧をそのまま値にしない。結果が同じになる状態はまとめる(決済済・注文なし・取消済 → 「確定」)。境目は値として立てる(「締め日の終わる 1 秒前」「締め日の終わり(ちょうど)」)。まとめた中身は `terms` か `note` に書く。
- **行は、自分が固定した値だけに印を付ける。** そのテストで意味を持たない因子は書かない(どの値でもよい)。
- **因子が 2 つ以上あるのに対角線になったら、因子の切り方が間違っている。** どの行も 1 列にしか印が無く、どの列も 1 行にしか印が無いなら、列が「テスト 1 件の状況」になっている。因子と値に分け直す。因子が 1 つの表は、1 行 1 列で正しい。

## 組み合わせ表

結果が 2 つの因子の組み合わせで決まる(片方だけでは決まらない)ときは、`combinations` にその 2 因子を書く。ページは縦に 1 つ目の因子の値、横に 2 つ目の因子の値を並べた表を作り、各マスに、その 2 つの値を両方固定した行の数を出す。行の無いマスは赤になる。

- **3 因子以上が絡むときは、2 因子ずつの表に分ける。** 全部の組み合わせを並べると、表が読めなくなる。
- **テストしなくてよいマスは `excluded` に理由を付けて書く。** 起こり得ない組み合わせ(「締め日の終わった後で、入力が未確定」に意味が無い、など)や、別の表で確かめる組み合わせ。理由の無い除外は書かない。
- **Theory の行が配列で複数の値を持つときは、組み合わせの数え方に注意する。** 配列は直積として数える(`{A: [a1, a2], B: [b1, b2]}` は 4 マスに数える)。Theory の各行が `(a1, b1)` と `(a2, b2)` だけなら、行を分ける。

## 合計の数え方

ページの合計は `cases` の和。同じテストを複数の表に載せたとき、2 回目以降の行を `cases: 0` にしないと二重に数える。`build_matrix.py` は数えた合計を出力するので、変更に含まれるテストの実際の件数(xUnit の結果ファイルや、テスト一覧の生成物)と突き合わせる。

値の列と組み合わせのマスが「テストあり」になるかは、`cases` ではなく行の有無で決まる(`cases: 0` の `s` の行も数える)。
