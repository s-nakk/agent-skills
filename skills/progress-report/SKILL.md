# progress-report

クライアント送付用の進捗報告を、指定期間内の実作業ログから生成する。

## 何をするスキルか

開発の進捗を「クライアントが読んで意味がわかる文章」に翻訳する。
素材（git コミット / 記憶 / セッション履歴）は手元にあるが、そのまま貼るとクライアントには理解されない。このスキルは、素材を集めて、機能名や DB 識別子を業務語に翻訳し、短い箇条書きとして出力する。

**出力はチャット内のテキストブロックのみ。ファイルには保存しない。** ユーザーが自分で Slack / メールに貼り付ける。

## 起動条件

以下のいずれかで起動する。

- `/progress-report` のスラッシュ呼び出し
- 「進捗報告作って」「クライアント向けにまとめて」「〜から〜までの作業をクライアント向けに整理」
- 「Slack に貼るやつ」「報告書送りたい」のような文脈で期間と一緒に依頼されたとき

## 期間の解釈

期間は **開始日時〜終了日時** で受ける。粒度は分単位（`yyyy-mm-dd HH:MM`）。

- ユーザーが期間を明示したらそれを使う。例: 「2026-04-20 23:20 〜 2026-04-21 09:30」
- 時刻が省略されたら、開始は `00:00`、終了は `23:59` として扱う
- 期間が曖昧（「今日」「今週」のみ等）なら一度だけ確認する。「`<開始>` 〜 `<終了>` で良いですか」と短く

## 対象プロジェクトの判定

実行時の cwd を見てプロジェクト名を決める。`pwd` の末尾ディレクトリ名をプロジェクト識別子として使う。

- cc-mnemos: `mcp__cc-mnemos__search_memory` の `project` フィルタに渡す
- git log: cwd で `git log` を直接叩く
- セッション履歴: 利用中ツールのセッション保存先を見る（必要時のみ。Claude Code なら `~/.claude/projects/<encoded-cwd>/`）

ユーザーが明示的にプロジェクトを指定（「<repo名> で」等）した場合はそれを優先。

## データ収集の手順

3 つのソースから素材を集める。並列に叩く。

### 1. cc-mnemos の記憶（導入していれば主要ソース）

[cc-mnemos](https://github.com/s-nakk/cc-mnemos) を導入している場合、`mcp__cc-mnemos__search_memory` を **複数のクエリで** 引く。導入していなければこのソースは飛ばし、git log を主要ソースにする。1 回では網羅できない。期間内に出てきそうな主要キーワードを 3〜5 個並列で投げる。

クエリ例:
- プロジェクトのコア機能名（「テナント 招待」「レポート出力」等）
- 「実装」「修正」「対応」「追加」「整備」を組み合わせた語
- 期間中に話題に上がっていそうな抽象テーマ

結果は `created_at` を見て期間内に絞る。**期間外の記憶は捨てる**。記憶のテキストから「ユーザーの依頼 → agent の対応 → 結果」の流れを読み、何が完了したかを抽出する。

### 2. git log

期間内のコミットを取る:

```bash
git log --since="<開始>" --until="<終了>" --no-merges --pretty=format:"%h %ad %s%n%b" --date=iso
```

複数ブランチを跨ぐ可能性があれば `--all` を付ける。直接 `git log` を使う。

コミットメッセージから「何が完了したか」を読む。同一機能の複数コミット（例: `feat:` → `fix:` → `refactor:` の連なり）は基本 **1 件の箇条書きに集約** する。ただし **`fix:` で「壊れていた挙動を直した」ものは、機能側に吸収せずバグ修正セクションに独立した行として立てる**（次節の振り分け参照）。機能側に畳んでよいのは、内部リファクタ・ビルド調整・文言だけの変更など「バグではない」コミット。`fix:` を機能の行に紛れ込ませると、クライアントから見たバグ修正の件数が消えてしまう。

### 3. 過去セッションの jsonl（補完）

cc-mnemos と git に出ていない情報があるとき（例: 仕様議論で実装には至っていない決定、未コミットの作業）に限り、利用中ツールのセッション履歴（Claude Code なら `~/.claude/projects/<encoded-cwd>/*.jsonl`）を期間で絞って参照する。優先度は低い。

期間判定: jsonl の各行に `timestamp` フィールドがある。期間内のメッセージだけ抽出。

## 集約とグルーピング

集めた素材から箇条書きを作る。

- **1 行 = 1 機能 / 1 基盤**: 粒度を揃える。1 行が画面 1 つ、機能 1 つ、基盤 1 つくらい
- **重複は統合**: 同じ機能を触る複数のコミット / 記憶は 1 行に集約
- **小粒は統合 or 切る**: 「typo 修正」「import 整理」等の単独だと意味を成さないものは捨てるか、上位機能の箇条書きに「等の整備」として吸収
- **テスト関連の扱い**: 手動 QA テストケース / 動作確認チェックリスト（xlsx・観点設計・生成スクリプト等）は **クライアント向けの品質成果物**として「その他」セクションに 1 行で出す。複数画面ぶんあれば「〇〇・〇〇の N 画面を追加」と集約する。**機能の行（ラベル変更・新機能追加など）に紛れさせて落とさない**。一方、TDD の自動テスト（単体 / 結合 / e2e）は内部のエンジニアリングで、クライアント価値に翻訳できないので **項目として出さない**
- **3 セクションに振り分ける**: 各箇条書きを「バグ修正」「改善・新機能」「その他」のいずれかに分類する。判定基準は次節。`(途中)` の項目も該当するセクションに入れる
- **セクション内の順序**: クライアント関与のあった項目（要件議論 / 仕様確認の結果実装したもの）を上位、基盤・裏方系を下位に置く

## バグ修正・改善・新機能・その他の振り分け

各箇条書きを 3 つのセクションに分ける。判定の軸は **「壊れていたものを直したか / 新しい価値を足したか / そのどちらでもない作業か」**。クライアントは「不具合対応」と「前に進んだ開発」を別物として読みたいので、混ぜずに分ける。

- **バグ修正**: 本来の挙動どおりに動いていなかったものを正す。「〜の不具合を解消 / 修正」と書けるもの。コミットの `fix:` の多くがここ。ただし `fix:` でも UX 改善・文言変更など「壊れてはいないが良くした」ものは改善側に置く（prefix だけで機械的に振り分けない）
- **改善・新機能**: 新規画面 / 新規機能の追加、既存機能の使い勝手・見た目の改善、基盤整備。`feat:` の多くがここ。クライアントが要件提供 / 仕様確認に関与した作業は基本ここに入る
- **その他**: 製品機能の追加・改善でもバグ修正でもないが、報告に値する作業。手動 QA テストケース / 動作確認チェックリストの作成・拡充が代表例。ドキュメント整備や調査・検証もここに入れる

迷ったら **「クライアントはこれを『直してくれた』と受け取るか、『良くしてくれた・増やしてくれた』と受け取るか、それ以外か」** で決める。

この振り分けは文章ルール 2（バグ報告は経緯を書かず結果だけ / 要件提供への関与は明示）と一貫している。バグ修正セクションの行は自然と「〜の不具合を解消」になり、改善・新機能セクションの行は関与を明示した文になる。

**バグ修正を機能側に吸収しない**: 新機能を作る過程で出たバグ（同じセッションで新規構築した画面の不具合など、クライアントが既に使っていたものではない場合）でも、「壊れていたものを直した」なら原則バグ修正セクションに独立で立てる。クライアントは経緯（新規開発中だったか既存機能か）を知らず「直してくれた」としか見ないため、件数を機能の行に埋めて消さない。畳んでよいのは内部リファクタ・ビルド調整・文言変更など「バグではない」もの。逆に `fix:` でも実体が UX 改善・文言変更なら改善側へ。**プレフィックスではなく実体で振り分ける**。

**素材が無いセクションは、見出しごと省略する**（空見出しを残さない）。バグ修正もその他も無い期間なら「◆ 改善・新機能」だけを出す。

## 文章ルール（最重要）

このスキルの価値はここに集約される。素材をそのまま並べるなら誰でもできる。クライアントが読んで嬉しい文章にするのが仕事。

### ルール 1: 技術語をクライアント価値に翻訳できないなら書かない

クライアントは「DB レベルで分離」「正本化」「CI で自動検知」「N+1 解消」が何かを知らない。書いてもノイズになるだけ。

判定: 各箇条書きを書いた後に「これを読んでクライアントは何が嬉しいかわかるか？」を問う。わからないなら削るか、翻訳する。

| 翻訳前（書かない） | 翻訳後（書く） |
|---|---|
| N+1 クエリを解消 | （価値が翻訳できないなら丸ごと削る） |
| Repository パターンを適用 | （内部実装パターン名は禁止） |
| Row Level Security を導入 | 権限を持たないユーザーが他テナントの情報に到達できない構造を二重で確保 |
| migration を当てて seed を更新 | 〇〇テーブルを新設し初期データを投入 |

### ルール 2: クライアント関与のある作業は「提供いただいた要件を〜に反映」と明示（バグ報告は例外）

クライアントが**要件提供 / 仕様確認**に関与した作業は、その関与を文章に出す。クライアントは「自分の話したことが届いた」を強く望む。

- ❌ 「権限設計を見直した」
- ✅ 「権限周りで**提供いただいた要件を確認し**、設計、DB スキーマ、既存実装に反映」

cc-mnemos 記憶やセッション履歴を読むときに、ユーザー（クライアント）からの要件提示が起点だったかを意識して抽出する。

**例外: バグ報告は報告経緯を書かず、結果だけ書く。** クライアントが不具合を報告した作業に「ご報告を受けて」「ご報告いただき」「原因を特定して」のような前置きは付けない。当然直すべきものを直しただけなので、経緯は冗長でクライアントの興味の外。

- ❌ 「〜の不具合をご報告いただき、原因を特定して解消」
- ❌ 「ご報告を受けて〜を解消」
- ✅ 「〜の不具合を解消」

「要件提供への関与は明示する」と「バグ報告の経緯は省く」は両立する。前者はクライアントの提案が成果に反映された価値、後者は直して当たり前という違い。

### ルール 3: UI 操作の細かい手順は省く

機能名で十分。手順はクライアントの興味の外。

- ❌ 「ダイアログから名称を入力するだけでテナントが作成できるよう実装」
- ✅ 「テナント新規作成画面を実装」

### ルール 4: 未完了のものは語尾に `(途中)`

「進行中」「実装中」「対応中」とは書かない。`(途中)` という同じシンボルで統一する。

期間終了時点で完了していないものは `(途中)` を付ける。期間内に完了したものは何も付けない。

- ✅ 「staging 環境への CI/CD 構築 (途中)」

### ルール 5: 「次は〇〇に着手予定」は書かない

主役は完了した成果。次回予定は対面 / 別チャネルで話す。書いても軸がブレるだけ。

### ルール 6: 実装方式の内部用語禁止

`Repository` / `UseCase` / `Handler` / `migration` / `seed` / `e2e` / `Refactor` / `Hook` のような実装パターン名は出さない。同義の業務語に置き換えるか、書かない。

### ルール 7: 1 箇条書きは短く。括弧の補足は最小限

各箇条書きは **1 行で読み切れる長さ** に収める。括弧の補足は本当に必要なときだけ最小限にし、説明を盛って長くしない。

- ❌ 「会話分析画面を刷新（話題が少数だと縦長の色ブロックに崩れていた表示をやめ、総会話数・未回答件数などのサマリと、FAQ化をおすすめする順に質問の話題を並べたグラフへ統合）」
- ✅ 「会話分析画面を刷新（FAQ化をおすすめする順に話題を並べたグラフと、件数サマリへ統合）」

判定: 括弧内が 1 文に収まらない / 「〜し、〜し、」と連なるなら長すぎる。要点だけ残し、改善前後の細かい経緯は落とす。

## 出力フォーマット

チャット内に以下のテキストブロックを出す。コードブロックで包んで、コピペしやすくする。順序は **バグ修正 → 改善・新機能 → その他** で固定。

```
進捗報告（<開始 mm/dd HH:MM> 〜 <終了 mm/dd HH:MM>）

◆ バグ修正
• <バグ修正 1>
• <バグ修正 2>

◆ 改善・新機能
• <成果 1>
• <成果 2>
• <未完了の作業> (途中)

◆ その他
• <テスト整備など 1>
```

- セクション見出しは `◆`（U+25C6）+ 半角スペース。順序は **バグ修正 → 改善・新機能 → その他** で固定
- 該当する素材が無いセクションは、見出しごと省略する（空見出しを残さない）
- 日付表記は `mm/dd HH:MM` 形式に圧縮（年は省略、同月内なら見やすい）
- 期間が長い場合は `yyyy/mm/dd 〜 yyyy/mm/dd` でも可
- 箇条書きは中黒 `•`（U+2022）を使う

### 出力直後の振る舞い

テキストを出した後、ユーザーが調整を求めることが多い。

- 「もうちょい削って」→ 上位の重要項目だけ残す
- 「これ追加して」→ ユーザー指定の項目を素材に戻す or 直接追記
- 「言い回しがクライアントに通じない」→ 該当行を翻訳し直す

ユーザーが OK と言うまで反復する。クライアントに送付してから戻ってきたフィードバックがあれば、それも次回以降のため 個人のルールファイル（Claude Code なら `~/.claude/rules/` 配下など）へ反映を提案する。

## 出力例

`references/examples.md` に、3 セクションすべてが揃う例と、改善・新機能だけの例を置いている。文章ルールの適用結果を確認したい時に読む。

## 注意事項

- **完了していないものを完了として書かない**。`(途中)` の運用厳守
- **必ず 3 セクションに振り分ける**。バグ修正 → 改善・新機能 → その他 の順。素材が無いセクションは出さない（空見出しを残さない）
- **網羅性 > 完璧性**。拾い漏れより書き過ぎを許容する
- **粒度を揃える**。1 行の大小が極端だと読みにくい
- **1 行は短く**。括弧の補足が複文・長文化したら要点だけ残す（ルール 7）。バグ報告に報告経緯を付けない（ルール 2 例外）
- **期間外の素材を混ぜない**。cc-mnemos / git / セッションいずれも `created_at` / commit date / `timestamp` で必ず期間絞り
- **ファイルに保存しない**。チャット内テキスト出力のみ。ユーザーが必要なら自分で保存する
