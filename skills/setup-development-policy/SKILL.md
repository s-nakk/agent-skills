# 開発方針の対話式セットアップ

共通方針とプロジェクトの運用選択を分け、初回に決めた選択を次回以降も使える状態にする。Issue、特定の言語、クラウド、端末、他の Skill を必須依存にしない。

## 調べてから質問する

指定されたプロジェクトを対象にする。未指定なら現在のプロジェクトを候補とし、複数候補から選べない場合だけ質問する。Skill の配置先を対象プロジェクトと取り違えない。

編集前に次を read-only で確認する。

- 実行中のツールに適用される上位・プロジェクト・子ディレクトリの規約と、Codex の `AGENTS.override.md` など優先する入口。別ツール用の規約は参考として区別し、機械的に統合しない
- 保存済み方針、manifest、lockfile、テスト・ビルド設定、CI、Git remote と現行差分。バージョン・コマンド・文書の場所は現物から取得し、secret 値は出力しない
- Git の有無、変更候補の追跡・ignore 状態。Git がなければ Git 操作や Issue を前提にしない
- 実際に agent が動く OS・シェル・利用可能なツール。Windows ネイティブ、WSL、macOS を区別し、端末間の導入・更新では [OS とパスの扱い](references/platforms.md) を読む

調査は導入に必要な範囲に限定し、Issue の存在確認だけのために外部サービスへ接続しない。今回の規約変更にも適用される既存の承認ゲート・Worktree 条件は守る。この Skill 自体は Issue や設計 HTML を一律に要求しない。

## 未確定の運用を対話で決める

[選択肢と判断基準](references/setup-options.md) を読み、各項目を既存規約で確定・この会話で指定済み・未確定・非該当に分ける。確定済みの項目を再質問しない。

未確定の項目だけ、利用可能な対話ツールの上限に合わせて少数ずつ質問する。既存運用に近い案を推薦し、違いを短く説明する。対話ツールがなければ通常の会話で質問する。推薦・初期選択・返答待ちの時間経過は回答ではない。回答前に依存する設定を保存せず、独立した調査や候補作成を進める。

再実行時は変更希望と新たな未確定項目だけを扱う。方針変更の依頼がなければ初回質問をやり直さず、現在の適用状態を報告する。

## 方針と差分案を組み立てる

[共通規約の配布原本](assets/core.md) と [プロジェクト設定の雛形](assets/project.md) を使う。Skill 配下の原本を個別プロジェクトの値で書き換えない。

既定の生成物は対象プロジェクト内の次の3点。同等ファイルがあれば重複作成せず統合する。

- `.agent-policy/core.md`：共通規約のコピー。プロジェクト固有名・絶対パスを持たない
- `.agent-policy/project.md`：回答、適用条件、検証コマンド、固有の正本、共通規約の版
- 現在のツールに有効な入口：Codex なら `AGENTS.md`、Claude Code なら `CLAUDE.md` など。既存本文を残し、上の2ファイルを読む短い案内を追加する

優先する override があれば通常の `AGENTS.md` だけを編集して反映済みとしない。有効な入口と変更許可の範囲を確認する。別ツールへの同時適用と GLOBAL の変更はユーザーが選んだ場合だけ行う。

パスはプロジェクトルート基準の相対パスとし、その基準を入口に書く。別端末のホームや Skill のインストール場所に依存させない。追跡対象の入口から参照する規約も共有する必要がある。local-only の選択と入口の追跡状態が両立しない場合は、勝手に untrack したり override を作ったりせず、不整合と選択肢を示す。

保存する選択、変更ファイル、既存規約との矛盾と解決案、未確認の能力を具体的な差分案で示す。Issue なしの通常作業、Git の完了地点、設計承認・独立レビューが必要になる条件が分かるようにする。

明示済みの選択と導入指示だけで確定する追記は、追加の形式的承認を求めず反映する。既存規約の削除・優先順位変更・未選択の操作・導入先の必須ゲートなど、判断が残る部分だけ具体案への回答を待つ。

## 保存と検証

既存本文と利用者の追記を保持して変更箇所だけ反映する。同じ内容で再実行しても案内・設定・共通規約を重複追記しない。共通規約の更新では配布原本との差分と独自変更を比較し、独自変更を上書きしない。

共有・ローカルの選択に従い、Git がある場合は `git ls-files` と `git check-ignore` で全生成物の保存境界を確認する。ローカル保存は既存の ignore または承認された Git の exclude 設定で扱い、追跡済みファイルを勝手に untrack しない。exclude の実パスは対象プロジェクトで `git rev-parse --git-path info/exclude` により解決する。Worktree では `.git` がファイルの場合があるため、`.git/info/exclude` を直接組み立てない。

導入後に次を確認する。

- 有効な入口から両規約へ到達し、相対パスが存在する。保留中の回答、未記入欄、未解消矛盾が残っていない
- Issue なしなら通常変更に Issue を要求しない。ローカル完了なら commit・push・PR を要求しない。設計承認とレビューは選んだ条件にだけ適用する
- 小さな修正は親だけで進め、委任は共通条件を満たす時だけ行う。必須レビューは例外として維持する
- 検証コマンドと適用条件が保存され、導入しただけで製品全体のテスト・本番操作・有料 API 呼び出しを起動していない
- 共有する方針に端末固有の絶対パスや未確認のシェル依存がない。OS ごとに異なるコマンドは実行環境と確認状況を区別し、他の OS の成功を推定していない

今回の規約変更自体に必要なレビュー・公開手順は導入前の規約と現在のユーザー指示に従う。新設定で今回の必須レビュー・承認を免除しない。将来の Git の完了地点を保存することだけを、今回の commit・push・PR 作成の許可と取り違えない。

生成先、確定方針、参照・保存境界の確認、実施したレビュー、残件を短く報告する。未解決の選択や必須ゲートがあれば導入完了とせず、作成済みの案と残件を区別する。別端末への反映やトークン削減を未測定で成功扱いにしない。
