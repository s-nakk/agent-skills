# 初回に決める運用

既存規約と現在のユーザー指示が優先。以下は未確定項目の選択肢であり、自動適用する既定値ではない。必要な質問だけを対話ツールの上限に合わせて分けて聞く。

| 項目 | 選択肢 | 保存する意味 |
|---|---|---|
| Issue | 使わない / 必要な時だけ / 変更前に必須 | 使わない場合、通常作業・設計・レビューに Issue 番号を要求しない。目的・範囲・完了条件は会話や既存の変更記録で揃える。必要な時だけなら、複数人の調整など起票する具体的条件を決める |
| 設計の事前承認 | 重要な変更だけ / すべての変更 | 重要な変更の候補は公開動作・API・DB・認証認可・外部副作用・移行に影響するもの。適用条件を確定する。すべての場合も read-only 調査まで承認待ちにしない |
| Git の完了地点 | ローカル変更 / commit / push / draft PR | ローカル変更は commit しない。commit はローカルまで、push は指定 remote の作業 branch まで。draft PR は ready・merge・auto-merge を含めない。Git がなければ非該当でローカル変更のみ |
| 作業場所 | 現在の checkout / 専用 Worktree | checkout は他者の差分を混ぜない。Worktree は base・作成場所・依存準備・撤去条件を既存設定から取得する。Git がなければ非該当 |
| 独立レビュー | リスクのある変更 / すべての実装変更 | リスクの候補は認証認可・外部 I/O・DB・公開 API・複数 component をまたぐ動作・回帰影響など。ファイル数だけで判定せず対象を明文化する。実行方法と入力も確定する |
| 保存範囲 | プロジェクトで共有 / この端末だけ | 規約と選択を Git に含めるかローカル管理にするか。入口と参照先の追跡状態を揃える。GLOBAL は明示希望がある場合だけ別対象とする |

これらは独立した選択。Issue なしでも draft PR は可能で、架空の `Refs #番号` を足さない。Git がなければ remote・PR・Worktree の質問をしない。

## 設計承認と Issue を結びつけない

設計を承認する条件と資料の形式・保存先は別の判断。既存形式を優先し、未指定なら規模に合う Markdown・会話内の具体案などを提案する。HTML や Issue 連携ディレクトリを必須にしない。

Issue なしで設計承認を行う場合は、変更を識別できる名前と版を使う。提示した対象版への返答を得たら同じ版を再承認させない。承認済み仕様・範囲を変える時は差分への判断を求める。

## 独立レビューの実行条件

親の経緯や結論を引き継がない別 context が必要。利用可能な Codex セッション、Claude Code の reviewer など対象ツールの機能を確認し、許可される方法を保存する。個人用 profile・未導入の Skill・モデル名を架空に指定しない。実装担当を独立 reviewer とみなさない。

- draft PR：実在する対象 PR と固定 head
- commit / push：base と head の commit
- ローカル変更・Git なし：read-only の固定ファイル snapshot と変更前後の差分。作成方法・対象・保存先を決め、レビュー中に内容を変えない

既存のレビュー Skill が PR や commit を必須とするなら、その Skill をローカル snapshot 対応とみなさない。別の利用可能な方法を確認し、なければ実行方法未確定として選択を残す。レビュー設定のために Git の完了地点を勝手に引き上げない。

## Skill の発動条件

Skill が導入済みでも、そのフローが採用済みとは限らない。Issue ベースの Skill や全変更向けの設計 HTML Skill を、選択した方針より優先させない。

生成する設定に「Skill は選択された条件に合う場合だけ使う。Issue なし・承認不要の変更へ、Skill の既定から Issue や設計ゲートを追加しない」と書く。適用される既存規約と矛盾する場合は解決案を示して確定してから保存する。導入先以外の Skill や GLOBAL を書き換えて解決しない。

## 保存して再質問を避ける

選択値・条件・根拠となる既存規約またはユーザー回答・配布版を残す。通常の開発では再セットアップしない。再質問は方針変更の依頼か、環境変化で実行不能になった該当項目だけに限る。
