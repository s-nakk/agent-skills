# 共通開発規約

配布版: 1

このファイルと同じディレクトリの `project.md` が共通方針と運用選択を定める。パスはプロジェクトルート基準。Issue・設計承認・Git・作業場所・レビューの条件は `project.md` に従い、他の Skill の既定で追加しない。適用される上位規約やユーザー指示との矛盾は、該当操作の前に具体的に示して解決する。

## 作業継続と根拠

- 調査・説明・review-only は read-only。実装依頼は許可された完了地点まで進め、可逆的な実装詳細や現物から確認できる事項でユーザー待ちにしない
- 目的・範囲・完了条件を変更規模に応じて揃える。Issue を使わないことを仕様や検証を省く理由にしない
- 承認は対象・操作・設計版の範囲で扱い、同じ条件を再確認しない。未回答を承認とみなさず、判断が必要なら具体案と根拠を先に揃える
- 現行コード・設定・データ・ログ・公式仕様を根拠にし、確認済み・推定・未確認を分ける。ライブラリの使い方は manifest と lockfile のバージョンを確認して調べる
- 必要な証拠が揃ったら調査を収束させる。同じ失敗の反復や、根拠のない探索範囲の拡大を続けない

## 設計と検証

- 既存構造に沿う最小の変更を行い、不要な抽象化・互換 shim・fallback を追加しない。外部入力は境界で検証し、実際の障害モデルに応じて timeout・retry・縮退を設計する
- リリース状態・利用者・保存済みデータを確認して互換性を判断する。必要なデータ移行・deploy 順序・rollback を設計する
- 名前と型で意図を表し、コメントは理由や守る境界を補う。形式的なコメントや無関係な整形を増やさない。言語固有の規約はプロジェクトの正本に従う
- バグ修正は可能なら再現テストを先に書き、期待する理由の失敗を確認してから直す。新機能は受け入れ条件を先に決める。純粋な文言・layout 変更へ形式的な Red test を要求しない
- 変更範囲の検証と既存の必須 check を実行する。通過後は追加変更・失敗・具体的な懸念がある場合だけ検証を広げる
- 新たな warning・error は解消し、無関係な既存問題は区別して報告する。local・CI の成功から staging・production・人手評価の成功を推定しない

## OS と実行環境

- 共通方針は Windows と macOS で共有し、シェル依存のコマンドは実際の OS・シェルとプロジェクト設定に合わせる。Windows ネイティブと WSL は別の実行環境として扱う
- 文書の参照はプロジェクトルート基準の相対パスと `/` を使い、端末固有のホーム・ドライブ・一時ディレクトリを共有規約へ固定しない。コマンドでは実行環境のパス規則と引用方法を使う
- 環境を移しても Issue・承認・Git・レビューの選択は維持する。実行できないコマンドやツールだけを見直し、別 OS の検証を実施済みとみなさない

## サブエージェント

- 既定は0体。親の文脈や判断への依存が強い作業、短い修正、直列工程は親が進める
- 通常作業は、少ない引き継ぎで完結する十分な大きさの独立作業で、親も別の有用な作業を進められ、追加消費に見合う時間短縮または調査範囲の拡大を説明できる場合だけ、この規約の指示として委任する。効果が不明なら親が続ける。ユーザーが委任を明示した場合は指定範囲に従う
- 親と子の調査を重複させず、関連作業は同じ子を再利用する。会話全文の機械的な複製を避け、目的・担当・前提・一次資料・完了条件を絞る
- 実装の担当ファイルと共有資源を分離し、他者の変更を戻さない。結果は結論・一次根拠・未確認事項を中心に返し、親が統合する
- キャッシュ命中を前提に節約を保証しない。主コンテキストの整理、時間短縮、総トークン削減を区別する
- 必須の独立レビューは独立性の追加コストとして別扱いにし、省略しない。実装経緯を引き継がない担当へ固定された対象を渡し、指摘対応は可能な限り同じ reviewer で確認する

## 変更権限と完了

- 変更前に追跡状態と既存差分を確認し、他者の作業や範囲外の変更を混ぜない。Git 操作は `project.md` の完了地点と今回の依頼に従う
- secret・認証情報・個人情報を commit しない。破壊的操作、本番の状態変更、通知送信、課金などは対象と操作への明示指示が必要。通常の実装・委任・レビューはその権限を追加しない
- 外部の Issue・PR の存在を、本文・状態・コメントの更新権限とみなさない。Issue なしの場合は起票や架空の番号を要求しない
- 指摘は契約内修正と仕様・範囲の変更に分ける。前者は修正と必要な再検証・再レビューへ進み、後者は具体的な差分への判断を求める
- 自分が起動した background process を記録して終了時に停止する。他者の process を終了しない
- 完了報告は結果、必要な根拠・検証・レビュー、残件を短く示す。未実施の検証・外部反映・トークン削減を成功扱いにしない
