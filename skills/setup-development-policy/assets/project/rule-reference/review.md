# プロジェクト補助規約 — review

プロジェクトの `AGENTS.md` の一部。適用対象・入力方式・起動方法は同じディレクトリの `settings.md` に従う。以下の PR・head の記述は PR モード、commit の記述は commit snapshot モードに適用し、ローカル snapshot モードでは固定した変更前後と差分をレビュー単位にする。Issue の参照は採用時だけ、設計版の承認ゲートは承認を採用した変更だけに適用する。

### 独立レビュー（リスク重み付き敵対的検証）

- Git 管理対象の変更では、通常は draft PR 作成後に独立レビューを開始する。PR が ready へ変更されていても、open かつレビュー開始時と終了時の head SHA が一致する場合は同じ PR をレビューし、draft へ戻すことを要求しない。reviewer は実装担当とは別の、実装の経緯を引き継がない context とし、PR の最終差分を read-only でリスク重み付きの敵対的検証にかける。敵対性は実装者の説明、test、CI を鵜呑みにしないことを意味し、反例の数ではなく merge 判断を変える現実的または重大な risk の発見を目的とする
- **完成候補だけを渡す**: 独立レビューは設計相談、実装途中の探索、既知問題の発見、通常の self-review の代わりに使わない。親 agent は、ユーザーの直近指示、明示的に否定された方式、Issue、仕様、実装、回帰テストを照合し、既知の未実装、設計判断待ち、失敗中の必須 check がない固定 head だけを初回レビューへ渡す。レビュー中は対象 head を変更しない
- **形態と収束条件の既定**: reviewer は初回レビュー時に Codex の新規セッションで起動し、同じ PR または変更タスクではそのセッションを差分再レビューに再開して使う。他のプラットフォームの agent を混ぜない。初回は PR 全体、その後は前回レビュー済み head から現 head までの差分だけを対象とし、blocker と親 agent が追加した未レビュー差分がなくなるまで同じ reviewer セッションで収束させる。回数上限によって未解消または未レビューの変更を残さず、設計や責務分担を変更しても PR 全体のレビューを最初からやり直さない
- **対象の既定**: 初回レビューは PR 全体、差分再レビューは前回レビュー済み head から親 agent が当該作業で追加した最終 head までだけを対象にする。差分には finding 対応だけでなく、初回レビュー後にユーザーが承認した方針変更と、それに伴う仕様・テストの更新を含めてよい。第三者の変更や当該作業と無関係な commit は対象へ取り込まない
- **変更契約の固定**: 親 agent は初回レビュー前に、Issue、長期仕様、ユーザーの直近指示から `必ず実現すること`、`採用しない方式`、`決定的テストが担う境界`、`live または人手評価が担う境界` を PR と仕様へ固定する。reviewer はその契約への違反を指摘できるが、契約を強化する追加ガード、別の実装方式、追加の回答強制を blocker として要求しない。契約自体の不足や変更が必要なら `設計判断が必要` として親 agent とユーザーへ返し、レビューと実装を往復させない
- **レビュー指摘後の設計差分ゲート**: 親 agent は初回レビューと差分再レビューの結果を受け取るたびに、修正へ着手する前に、各対応案を最後にユーザーが承認した設計版、Issue、長期仕様、変更契約と照合する。外部振る舞い、component の責務、主要データ、処理順序・判断条件、正常経路、失敗・縮退経路、安全性・互換性・移行、scope・非 scope、受け入れ条件、test と live・人手評価の責務境界のいずれかが変わる対応は、実装の大小や reviewer の severity にかかわらず `設計差分` とする。追加ガード、fallback、retry、schema 強化、責務移動、別方式への置換、契約を新設する否定例や test の追加も同様とする
- `設計差分` が一つでもある場合は、source、test、仕様、PR 本文を変更せずレビュー対応を停止する。親 agent は、承認済み設計から変わる点、変更理由、利用者・運用・安全性・互換性への影響、代案、推薦案を説明し、同じ変更の一時設計ディレクトリへ次版の設計資料を追加して提示する。ユーザーがその版を明示的に承認した後だけ修正と差分再レビューを再開する。reviewer の blocker 判定、CI failure、修正が小さいこと、既存の実装依頼は設計差分の承認を代替しない
- 承認済み設計の振る舞いと境界を変えず、実装をその契約へ一致させるだけの局所修正は、設計差分ではなく `契約内修正` として通常の修正・再検証・差分再レビューへ進めてよい。分類に確信が持てない場合は設計差分として停止する
- **差分再レビューで扱う finding**: blocker は、前回 finding の未解消、現差分が直接持ち込んだ regression、受け入れ条件との直接矛盾、または P0/P1、tenant 越境、漏えい、人の安全、データ消失に限定する。未変更範囲の新規 P2、以前のレビューで見落とした改善案、契約にない強化案を追加しない。指摘対応で head を更新した場合は、設計差分ゲートを通したうえで、同じ reviewer セッションを再開してその差分をレビューする
- reviewer は実装の経緯を引き継がない別 context であることが条件で、親 session 自身による self-review は代わりにしない
- Codex の起動方法は `settings.md` に確認済みのコマンドと read-only 制限を記録する。`independent-final-review` を採用した場合は、その Skill と利用中の CLI が指定する起動・再開手順に従う。親の端末の profile 名・配置先を推測で引き継がない。profile または reviewer session の再開が利用不能なら、権限を広げたり別 reviewer へ切り替えたりせず未完了を報告する
- review prompt に渡す変更情報は、初回レビューでは PR の URL または番号だけ、差分再レビューでは同じ reviewer セッションへ PR の URL または番号と前回レビュー済み head SHA だけとし、それ以外の例外を設けない。スキル指定と memory・他の過去ログを使わない実行指示以外に、実装の経緯、実装者の評価、検証結果の要約、想定する指摘や結論を渡さず、reviewer が PR、リンクされた Issue、仕様、差分、CI から事実を再構成する
- reviewer は同じレビューサイクルにおける自身の前回レビューの context を判断の一貫性と指摘の追跡に使う。それ以外の過去のセッション、rollout summary、memory は参照せず、PR と repository の一次資料だけで、仕様適合、設計、regression、security、類似ケース、範囲外差分を確認する
- reviewer は受け入れ条件と変更契約ごとに失敗仮説を立てるが、観点を一律に当てはめない。旧 client はリリース済み契約がある場合、保存済みデータは実在する場合、race、retry、timeout は並行処理、非同期処理、external I/O がある場合、deploy 順序と rollback は変更がそれらへ依存する場合だけ深掘りする。blocker は明示された契約または受け入れ条件、公開境界から現実的に到達する再現経路、影響を示す一次証拠をそろえる。証拠がない可能性や、より強い保証を実現できるという理由だけでは blocker にしない
- finding は、リリース済み契約、通常操作、実在する保存済みデータ、または現実的な障害モデルから到達でき、影響が無視できず、再現条件と一次根拠があり、発生条件が現実的である場合に限る。低確率でも tenant 越境、secret・個人情報漏えい、人の安全、データ消失、不可逆な migration など影響が重大なら finding にできる。理論上到達可能なだけの状態、公開境界から到達不能で契約上も生成されない未サポート内部入力、根拠なく複数の独立障害を重ねた状態、影響が軽微な問題は finding にせず、不要な互換 shim や defensive fallback を提案しない
- P2 を blocker にできるのは、受け入れ条件またはリリース済み契約を現実的な経路で破る場合に限る。P3 相当の改善案は独立レビューで報告しない。未検証境界は判定を左右するものだけを報告し、敵対的検証を live 環境への攻撃、状態変更、負荷試験へ拡張しない
- PR を作らず commit を許可した Git 管理変更では、repository のパスと base・head の commit SHA だけを変更情報として渡す
- commit しない変更では、`settings.md` で確認済みの独立 reviewer へ固定した変更前後ファイル・差分とユーザー依頼を渡す。追跡予定の変更を個人設定と偽って既存 Skill の入力制限を迂回しない。その入力を扱えなければ、review 未完了として具体的な不足を報告する
- 個人ローカル専用モードを採用した場合は、対象ファイルの絶対パスとユーザーの依頼だけを新規セッションへ渡す。Git 管理対象の未 commit 変更はこのモードへ混ぜず、確認済みの固定ファイル snapshot 方式を使う。実装の経緯や self-review はどの方式にも渡さない
- 親 session 自身による self-review は独立レビューとして扱わない
- 設計差分ゲートで `契約内修正` と分類できた仕様内の blocker は、親 agent が修正、再検証し、PR モードでは同じ open PR へ commit と push、commit snapshot モードでは新しい head commit を作成する。ready PR への追加 push はユーザー確認規約に従う。その後、同じ reviewer セッションを再開して差分再レビューまで進める
- 仕様変更、範囲拡大、破壊的判断が必要な指摘は `設計差分` として扱い、承認前に変更しない
- レビュー後に親 agent が当該作業の変更を追加した場合は、その時点の全差分を同じ reviewer セッションの差分再レビューへまとめる。各差分レビューの開始後は対象 head を変えない。第三者の変更や無関係な commit で head が変わった場合は取り込まず、対象範囲が変わったことを報告して停止する
- レビューサイクルの完了前に、親 agent は最終 head を承認済み設計の全版と照合する。設計差分がないこと、またはすべてが対応する版で追加承認済みであることを確認し、PR 本文と完了報告に `承認済み設計版`、`レビュー起因の設計差分`、`追加承認の有無` を記録する。未承認差分または照合不能があればレビュー完了とせず、修正や完了報告へ進まない
- 独立レビュー必須の変更では、reviewer または指定スキルが利用不能、初回レビュー未実施、再現可能な blocker 未解消、親 agent が追加した未レビュー差分、設計差分ゲート未完了のいずれかが残る状態で完了報告を行わない。判定を左右しない未確認や改善案は risk として報告し、追加ガードで自動的に埋めない
